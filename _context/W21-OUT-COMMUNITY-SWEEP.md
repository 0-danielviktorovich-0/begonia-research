**A working internal-WiFi monitor on a gen4m device EXISTS publicly as of Aug 2026**: [TheThunderstormX/mt6789-wifi-monitor](https://github.com/TheThunderstormX/mt6789-wifi-monitor) — Redmi Note 13 Pro 4G / POCO M6 Pro (`emerald`, MT6789/Helio G99, connac2-class, wlan_drv_gen4m), **root-only, no external adapter, 2.4 GHz capture verified on-device** (162 frames / 6 APs in an 8 s hop, no panic), 5 GHz hop-discovery works, 5 GHz data-lock open. ## 2. Ask-by-ask

### Ask 1 — GitHub patch/repo enabling monitor in gen4m Android kernels
**FOUND [V]: TheThunderstormX/mt6789-wifi-monitor** (§1 rows 1–4). Mechanism (no cfg80211 monitor — RFCR open via `set_mcr` + kprobe RX tap) **bypasses** the gen4m gap we recorded in 13 §1.5 (`gl_cfg80211.c` registers no `NL80211_IFTYPE_MONITOR`). Queries that found it: `mediatek gen4m wifi driver monitor mode NL80211_IFTYPE_MONITOR github`, `site:github.com wlan_drv_gen4m monitor packet capture radiotap`. Non-finding confirmed elsewhere: rotated passes (`wlan_drv_gen4m monitor mode patch android`, `site:github.com gen4m monitor sniffer radiotap`, `site:github.com nicRxEnablePromiscuousMode OR wlanSetPromiscuousMode OR "gl_cfg80211" monitor`, `"mt6789-wifi-monitor" OR "monx4" OR "monx.ko"`) surface **only this repo** — it is the unique public gen4m artifact; grep.app still Vercel-blocked.

**Portability to begonia [I, medium]**: all target symbols exist verbatim in begonia's gen4m (row 18). Differences to solve: (a) begonia chip = **CONNAC** (connac1-class connsys) vs emerald **connac2** — RFCR `0x820f5000` is connac2-empirical, must be relocated by the repo's own snapshot-differencing method; (b) `SW_RFB+0x18` offset must be re-checked against begonia's `sw_rfb.h`; (c) 4.14/4.19 kprobes fine; kallsyms root-readable with root. The repo's HQA tooling (`hqax`, cmd `0x1300` read / `0x1301` write) matches gen4m's legacy HQA path — likely usable on begonia too [I, low-medium].

### Ask 4 — begonia's exact WiFi chip variant
**Pinned at build level [V, high for class; part number = connsys of MT6785]**:
- `drivers/misc/mediatek/connectivity/Makefile` in both cloned begonia kernels: `CONFIG_MTK_COMBO_WIFI_HIF=axi`, `MTK_COMBO_CHIP=CONNAC`, `WLAN_CHIP_ID=6785` (+ `WIFI_IP_SET=2`, `WIFI_ECO_VER=1`); los-4.19 gates gen4m on `CONFIG_MTK_COMBO_CHIP_CONSYS_6785` (row 16).
- dts: `wifi@18000000` compatible `mediatek,wifi` on the AXI connsys block + `consys@18002000` `mediatek,mt6785-consys` — no SDIO slot, no discrete part (row 17).
- Defconfigs set `CONFIG_WLAN_DRV_BUILD_IN=y` and leave every discrete `MTK_COMBO_CHIP_*` unset — the platform Makefile overrides the Kconfig menu, resolving the §1.1 ambiguity.
**Correction to 13 §1.1 [I, high]**: "MT7663-family suspected" is now **wrong as a discrete-part hypothesis** — begonia's WiFi is the MT6785 **SoC-internal connsys built as chip=CONNAC, HIF=AXI**. It shares the gen4m driver but is not mt76-able (mt76 has no connac1-connsys driver; only connac2 fw-class parts in mt79xx/mt76xx-discrete). Firmware naming should follow `WIFI_RAM_CODE_*` on-device check for the exact RAM-code file — still the one open on-device item.
