# RFC 001 — рефакторинг структуры репозитория и двуязычной базы знаний

**Статус: ПРОЕКТ АРХИТЕКТУРЫ; массовая миграция файлов ещё НЕ выполнена.** Проверка исходного состояния: 21 ноября 2026 года.  
**Языки:** [Русский (этот документ)](repository-refactor-plan.md) · [English — original specification](../../en/architecture/repository-refactor-plan.md).

## 1. Что именно сейчас не так

В корне репозитория лежат **38 файлов**: 25 исследовательских документов с номерами 00–24, два README, общий INDEX, машинные JSON и пять CSV-таблиц. Ещё два файла называются `docs/en/README.md` и `docs/ru/README.md`. При этом `00-README.md` — технический обзор исследования, а не стартовая страница GitHub.

Именно поэтому пользователь видит ощущение дублирования. GitHub автоматически показывает корневой `README.md` при открытии репозитория; никакой необходимости хранить несколько корневых README нет.

**Цель — единственный `README.md` в корне**, предназначенный для знакомства с проектом, и две полноценно индексируемые языковые версии внутри `docs/en/` и `docs/ru/`.

Важно: разные языковые версии документов **не дублируют независимые исследования**. У темы есть постоянный ID и один оригинал, а переводы привязаны к конкретной версии оригинала.

## 2. Рекомендуемая архитектура

```text
begonia-research/
├── README.md                     # единая главная страница; EN / RU переключатель
├── LICENSE                       # лицензия кода
├── LICENSE-DOCS                  # лицензия текстов
├── NOTICE.md                     # права и атрибуция
├── .github/workflows/            # CI для ссылок, переводов и каталогов
├── docs/
│   ├── en/
│   │   ├── index.md             # поиск и тематическая карта на английском
│   │   ├── android/             # MIUI, CFW/Non-CFW, GSI, ROM и root
│   │   ├── kernels/             # 4.14, 4.19, 6.x/7.x, драйверы
│   │   ├── linux/               # Ubuntu Touch, Droidian, postmarketOS
│   │   ├── recovery/            # BROM, recovery, безопасность
│   │   ├── research/            # источники, аудиты, контакты разработчиков
│   │   ├── tools/               # ИИ-агенты, NetHunter и RE
│   │   └── architecture/        # архитектура базы знаний
│   └── ru/
│       ├── index.md             # русский поиск и каталог
│       └── ...                  # те же тематические категории
├── data/
│   ├── catalog/                 # источники, ID, индексы для агентов
│   └── matrices/                # CSV: firmware, kernel, hardware, root
├── i18n/                        # терминология, статусы переводов, правила проверки
├── research/
│   ├── evidence/                # архивы первоисточников и их контрольные суммы
│   ├── cache/                   # временные выгрузки веб-ресерча
│   └── agent/                   # история работы агентов, требования, контекст
└── tools/                        # утилиты и валидаторы
```

**Принцип разделения:** документация для читателя — в `docs/`; проверенные структурированные факты — в `data/`; оригинальные выгрузки сайтов — в `research/evidence/`; контекст Hermes/других агентов — в `research/agent/`; инструменты — в `tools/`.

**Не надо копировать целые исходники внешних ядер в этот исследовательский репозиторий**: для них фиксируются ссылка, ветка, SHA, лицензия, требования к сборке и результат проверки. Отдельный kernel-development репозиторий можно создать при реальной разработке.

## 3. Карта переноса существующих документов

Сохраняем номера 00–24 как исторические ID — не теряем привязку старых ссылок, чатов и агентов. Примеры:

| Текущие документы в корне | Целевая папка |
|---|---|
| 00, 01, 09, 17, 23, 24 (обзоры, источники, проверки) | `docs/en/research/` |
| 02, 10 (история прошивок и инструкции) | `docs/en/android/` |
| 03, 04, 11, 14 (ядра, драйверы, vendor, mainline) | `docs/en/kernels/` |
| 05, 06, 08, 15 (Linux-порты и разработка) | `docs/en/linux/` |
| 07, 18 (восстановление и проверка телефона) | `docs/en/recovery/` |
| 12 (инструменты и навыки) | `docs/en/tools/` |
| 13, 16 (NetHunter и Android root) | `docs/en/android/` |
| 19 (русский словарь CFW/GSI/Non-CFW) | `docs/ru/android/` |
| 20, 21, 22 (русские исследования root, NoMount и переноса ядра) | `docs/ru/kernels/` |

Для уже существующих английских переводов 19–22 используются те же предметные папки `docs/en/android/` и `docs/en/kernels/`. Русский подробный обзор документа 24 переносится в `docs/ru/research/`. **Оригинал 19–22 остаётся русским**, поскольку они были первоначально написаны по-русски; принудительно объявлять английский краткий пересказ оригиналом неправильно.

Другие файлы:

- `README.md` остаётся единственной главной страницей в корне. Его нужно сократить до введения, кнопок языков, состояния проекта и ссылок.
- `README.ru.md` объединить с `docs/ru/index.md`, затем убрать из корня **после исправления всех ссылок**.
- `docs/en/README.md` и `docs/ru/README.md` переименовать в `docs/{lang}/index.md`.
- `INDEX.md` превратить в генерируемый тематический индекс, не редактируемый вручную отдельно от данных.
- `index.json`, `sources.json` переместить в `data/catalog/` **после** обновления всех потребителей.
- CSV (`firmware-matrix`, `kernel-matrix`, `hardware-support-matrix`, `kernel-root-provenance`, `saikrishna-source-inventory`) — в `data/matrices/`.
- `archive/`, `_cache/`, `_context/` переносить **последними**: эти папки могут использовать работающие агенты и сборщики данных.

Перед удалением старых путей создаётся машиночитаемая таблица `data/catalog/path-migrations.json` с прежним/новым путём, состоянием миграции и контрольными суммами. Старые GitHub-ссылки вида `blob/main/старый-путь` **могут перестать открываться**: автоматическое перенаправление для любого переименования гарантировать нельзя. Временные файлы-указатели по прежним адресам упрощат переход, но в конце должны быть удалены, если приоритет — абсолютно чистый корень.

## 4. Порядок реализации

**Этап A — инвентаризация, без переносов.** Сохранить SHA исходной ветки и список файлов, собрать все внутренние Markdown/HTML-ссылки, ссылки в CSV/JSON, конфигурациях GitHub Actions, инструкциях Hermes и истории поиска. Зафиксировать таблицу переименований. До окончательного переноса обеспечить автоматические проверки.

**Этап B — исправить README и навигацию.** Сделать `docs/en/index.md` и `docs/ru/index.md`. Сохранить уникальную информацию из `README.ru.md`, заменить старые ссылки, удалить лишний корневой README. Корневой `README.md` должен оставаться кратким и полезным.

**Этап C — перенести отчёты одной проверяемой транзакцией Git.** Выполнить `git mv` и исправить относительные пути в перемещённых документах и в тех, что на них ссылаются. Сохранить номера, авторство, исторические ссылки и идентификаторы. Все поля `original.path`, `locales.path`, `derived_from_blob`, `source_file` обновить согласованно с изменёнными Git Blob SHA.

**Этап D — перенести машинные данные.** После обновления скриптов и CI переместить JSON/CSV. Архив и папки агентов переносить только после синхронизации с Hermes, чтобы он не продолжал записывать файлы по старым путям.

**Этап E — проверить и завершить.** Пройти автоматические проверки, открыть русскую и английскую стартовые страницы и типовые темы, отдельно проверить архивы, контекстные файлы и ссылки. Удалить временные старые маршруты только после контроля результатов.

Это должен быть **поэтапный рефакторинг**, а не хаотическое удаление файлов в GitHub.

## 5. Обязательные проверки качества

- Каждая внутренняя ссылка Markdown должна вести на существующий файл; каждый якорь — на реальный заголовок (включая заголовки на кириллице).
- Все **43 тематических ID** должны сохраниться в обеих языковых версиях индекса; русские и английские названия и поисковые ключевые слова — не теряться.
- Все **244 URL первоисточников**, имеющиеся на дату проектирования, должны остаться; любое дополнение или удаление проверять отдельно.
- Каталог переводов должен сохранять статус оригинала, черновика, краткого пересказа или полностью проверенного перевода. Если текст оригинала меняется, его Git Blob SHA меняется и перевод должен быть помечен как требующий проверки.
- CSV/JSON должны иметь корректную структуру, стабильные имена полей и индексы.
- GitHub Actions должны учитывать новые пути, включая проверки на pull request; проверять наличие выполнения, а не просто существование YAML.
- Никакого изменения смысла технических утверждений о совместимости ядер только ради переноса файлов.

## 6. Повторная проверка официального LineageOS и Linux 4.19

Здесь пользователь правильно заметил: **официальный репозиторий LineageOS для MT6785 действительно содержит Linux 4.19.325**.

Проверено непосредственно по `Makefile`:

- [`lineage-23.2`](https://github.com/LineageOS/android_kernel_xiaomi_mt6785/blob/lineage-23.2/Makefile): `VERSION=4`, `PATCHLEVEL=19`, `SUBLEVEL=325`.
- [`lineage-24.0`](https://github.com/LineageOS/android_kernel_xiaomi_mt6785/blob/lineage-24.0/Makefile): также **4.19.325**.
- [`rosemary_defconfig`](https://github.com/LineageOS/android_kernel_xiaomi_mt6785/blob/lineage-24.0/arch/arm64/configs/rosemary_defconfig) использует аппаратный вариант `mediatek/rosemary`, а [официальное описание устройства LineageOS](https://github.com/LineageOS/lineage_wiki/blob/main/_data/devices/rosemary_variant1.yml) относит это ядро к **Redmi Note 10S (rosemary)**. Большой список GitHub-файлов был обрезан по лимиту, поэтому полное отсутствие begonia-патчей где-либо внутри дерева этим не доказано.
- [`Saikrishna1504/device_redmi_begonia@axion/BoardConfig.mk`](https://github.com/Saikrishna1504/device_redmi_begonia/blob/axion/BoardConfig.mk) указывает сборку begonia с конфигурацией **k419**, а коммиты 13–15 ноября документируют адаптацию `init`, SELinux, UClamp, питания и DTBO. Подробности — [исследование 24](../../en/research/24-SAIKRISHNA1504-DEVICE-STACK-AUDIT.md). **Полный публичный kernel-tree 4.19 и обязательный `vendor/begonia.config` пока не найдены**, а старый манифест автора всё ещё указывает на ядро 4.14.357.

То есть: **Linux 4.19 для MT6785 проверен**, работа по переносу на begonia проверена, но полная воспроизводимая сборка именно для begonia остаётся отдельной задачей.

## 7. Решение

Рекомендую утвердить эту схему как целевую. **Данный документ — проект миграции, а не отчёт о завершённой уборке корня.** Перед реализацией следует обеспечить тесты, карту ссылок и отсутствие конфликта с работающими агентами; после этого переносить отдельными проверяемыми коммитами, не теряя историю.
