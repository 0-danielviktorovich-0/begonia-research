# Kernel Lab — автономная отладка Android/Linux на Redmi Note 8 Pro

**Статус:** проект архитектуры, а не запущенная система. **Дата исследования:** 2026-11-23. **Устройство:** begonia / MT6785. **Целевая платформа управления:** Mac. **Ядра:** Linux 4.14, отдельно экспериментальное 4.19.

**Статус перевода:** подробный русский конспект (не дословный полный перевод). Полный англоязычный технический документ: [Autonomous Kernel Lab](../../../en/tools/kernel-lab-autonomous-debugging.md). Конкретное задание для агентов: [Agent Mission (EN)](../../../en/tools/kernel-lab-agent-mission.md). Команды диагностики macOS: [Mac runbook (EN)](../../../en/tools/kernel-lab-macos-inventory.md).

## Цель

Создать единую инфраструктуру, чтобы AI-агент мог исследовать исходники и Kconfig, собирать экспериментальное ядро, наблюдать телефон, автоматически классифицировать состояние USB/ADB/recovery/fastboot, сохранять **первый crash**, анализировать причину и впоследствии — после отдельного безопасного допуска — возвращать проверенный рабочий boot image.

**Физическое ограничение:** если ядро не исполняется и устройство не предоставляет ADB/fastboot, команда с компьютера сама по себе не попадёт внутрь телефона. Для полной автономности в таких случаях понадобится отдельный проверенный аппаратный механизм, либо доступная независимая стадия загрузки. Ни один набор программ не гарантирует восстановление после абсолютно любого кирпича.

## 1. Проблема перезаписи логов recovery

Да, recovery запускает **собственное ядро Linux** и потенциально может использовать ту же область `ramoops`, что обычный Android. Console/ftrace — кольцевые буферы; новые сообщения могут вытеснить предыдущие. По официальной документации ramoops для Linux 4.14, после перезагрузки сбрасывается счётчик crash-записей, из-за чего последующие аварии способны перезаписать старые.

**Crash Vault:**

1. Проверить фактическую карту памяти MT6785, `reserved-memory` и MediaTek AEE/MRDUMP. Нельзя задавать физический адрес по догадке.
2. Сверить **оба** ядра и DTB: Android и recovery должны интерпретировать области pstore согласованно.
3. Встроить в самый ранний безопасный этап запуска recovery сборщик, который **до остального логирования и ротации** копирует оригинальные pstore-данные в отдельную область.
4. Создавать уникальный каталог попытки: ID, Git SHA сборки, конфиг, DTB, boot reason, raw pstore, SHA-256 и результат сохранения.
5. После безопасной инициализации носителя переносить архив на microSD. Затем или параллельно — на Mac. При наличии разрешённого внутреннего хранилища возможна дополнительная копия.
6. При недоступности SD или Mac не затирать исходные данные и не проводить бесконечные тесты вслепую. Первый сбой важнее десяти последующих.

Нельзя рассчитывать, что запись на SD прямо из обработчика kernel panic всегда безопасна: драйвер MMC, память или файловая система уже могут быть повреждены. SD — **послеаварийный архив**, а не универсальная замена ramoops.

В Android Open Source Project существует `recovery-persist`, переносящий часть pstore в постоянное хранилище. Это полезный образец, но его присутствие в конкретном TWRP/OrangeFox нужно проверять.

## 2. Почему телефон пропадает при переходе в recovery

Нужно различать минимум четыре случая:

| Наблюдение | Возможная причина | Действия агента |
| --- | --- | --- |
| В `adb devices` ничего нет, но Mac видит USB | ADB-сервер, USB gadget или recovery adbd | Сравнить USB VID/PID; перезапустить host ADB; проверить recovery init |
| Ни ADB, ни USB-устройства | USB-инициализация не удалась или устройство не работает | Проверить порт/хаб; при разрешении переключить конкретный USB-порт |
| Видно `fastboot devices` | Загрузчик исполняет fastboot | Проверка модели и возможностей; только отдельно разрешённое восстановление |
| MediaTek Preloader/BROM | Отдельная ранняя стадия загрузки | Сбор сведений и отдельная процедура восстановления, не обычный ADB |

На Mac полезны:

```sh
adb devices -l
fastboot devices -l
ioreg -p IOUSB -l -w 0
system_profiler SPUSBDataType
```

Если подвис только host ADB:

```sh
adb kill-server
adb start-server
adb devices -l
```

Если требуется физическое USB-переподключение, но хочется обойтись без рук — изучить [uhubctl](https://github.com/mvp/uhubctl) и совместимый USB-хаб с программным переключением конкретного порта:

```sh
sudo uhubctl                      # Только инвентаризация
# После точного определения порта и явного разрешения:
sudo uhubctl -l <hub> -p <port> -a cycle
```

Обычные USB-хабы могут не поддерживать это. Переключение USB не означает, что работающий от батареи телефон обязательно выключится или перезапустится. Нельзя без проверки переключать все порты Mac.

## 3. Автономное переключение режимов

Пока Android/recovery ADB отвечает, обычные варианты:

```sh
adb reboot recovery
adb reboot bootloader
```

Когда отвечает bootloader fastboot, используются **только подтверждённые данной прошивкой** fastboot-команды. Не считать `fastbootd`, `fastboot reboot recovery` и USB BootROM универсальными для begonia.

Для автономного rescue без ADB/fastboot могут понадобиться:
- аппаратный watchdog и корректная политика аварийной перезагрузки;
- устройство-независимый supervisor на Mac;
- однозначно опознанный USB-хаб;
- опциональный электроизолированный контроллер аппаратных кнопок / reset (после отдельного исследования платы).

Это существенно разумнее, чем роботизированная рука, но всё равно зависит от электроники и загрузчика.

## 4. UART на begonia

В доступной схеме упоминаются `UTXD0` и `URXD0` для Application Processor. Но **где находятся доступные UART-площадки на реальной плате Redmi Note 8 Pro, какое у них напряжение и активирована ли консоль — пока не подтверждено**.

Обычный кабель USB-C не превращается автоматически в UART. Не вскрывать аппарат и не подключать 5-вольтовый TTL-адаптер по догадке. Сначала нужны точная карта площадок, измерения уровней, проверка `console=`, `earlycon`, `stdout-path` и драйвера MTK UART. Если понадобится доступ к контактам, это отдельный аппаратный этап.

## 5. Автоматизация Kconfig вместо menuconfig

Белое меню, которым ты пользовался, — `make menuconfig`. Но агенту эффективнее работать через:

- `scripts/config` — точечно записать параметры;
- `scripts/kconfig/merge_config.sh` — объединить дефолтный конфиг и отдельный профиль;
- [Kconfiglib](https://github.com/ulfalizer/Kconfiglib) — программно прочитать символы, зависимости, ограничения и значения;
- `make ARCH=arm64 O=<out> olddefconfig` — нормализовать конфигурацию настоящим Kbuild.

Важно: `scripts/config` сам **не включает все зависимости**. А `olddefconfig` может выключить параметр, если условия не выполнены. Поэтому агент обязан **сравнить запрошенную конфигурацию с итоговой** и останавливать сборку при расхождении, а не продолжать вслепую.

Профили: `production` (минимальная нагрузка), `debug` (pstore/ftrace/AEE), `deep-debug` (тяжёлые диагностики по возможности). Под каждым профилем сохранять исходный коммит, `.config`, `vmlinux` с символами, DTB и контрольные суммы.

## 6. Инструментарий

| Средство | Назначение |
| --- | --- |
| Linux 4.14 `pstore/ramoops` | Сохранить часть аварийных данных между перезагрузками |
| MTK AEE / MRDUMP | Проверить уже имеющийся MediaTek механизм исключений/дампов |
| ftrace / dynamic debug | Понять последовательность функций и события драйверов |
| KGDB / KDB | Отладка ядра при наличии подходящего отладочного транспорта |
| KASAN / Lockdep | Проверки ошибок памяти и блокировок в отдельном debug-образе |
| `addr2line`, GDB, `vmlinux` | Привязать адреса стека к конкретным исходникам |
| `git bisect` | Выделить первое воспроизводимое плохое изменение |
| `uhubctl` | Разорвать/восстановить USB-соединение на совместимом хабе |
| [mtkclient](https://github.com/bkerler/mtkclient) | Исследование MTK Preloader/BROM; не универсальный автоматический unbrick |

## 7. Правила безопасности

Проект `begonia-research` является исследовательской базой, а не автоматическим прошивальщиком. Здесь можно добавлять архитектуру, матрицы, инструкции, безопасные прототипы и тесты на mock-данных. Но запрещено по умолчанию поручать автономному агенту стирать и перезаписывать `preloader`, `nvram`, `nvdata`, `persist`, RPMB, пользовательские данные, таблицу разделов или менять AVB/anti-rollback. Аварийные дампы также могут содержать личную информацию: хранить их приватно и очищать от секретов перед публикацией.

**Критерий готовности первого этапа:** агент исследовал исходники и текущую recovery, классифицирует USB-состояния на Mac, собирает read-only сведения, валидирует Kconfig и умеет архивировать тестовые дампы с контрольными суммами. Автономное восстановление настоящего bootloop — следующий отдельный этап, только после проверки резервной копии и механизма отката.
